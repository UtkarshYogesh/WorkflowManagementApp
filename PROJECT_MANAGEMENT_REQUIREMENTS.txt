Project Management App Requirements and Feature Checklist
========================================================

Purpose
-------
This document defines the product direction for the project management app.
Use it as a checklist to verify whether each feature is implemented completely.

The app is a lightweight organization-wide project management system.
It helps users see projects, create features, plan backlog items, create tasks,
assign work, update progress, and track status.


1. Product Problem
------------------
The app solves this problem:

- The organization needs one place to track all projects.
- Users should be able to see what work is happening across the organization.
- Admins should control projects.
- Users should collaborate on features, backlog items, and tasks.
- Work should have ownership, status, history, and clear permissions.

The app should answer:

- What projects are active?
- What features are planned or in progress?
- What backlog items exist under each feature?
- What tasks need to be done?
- Who created the work item?
- Who is assigned or responsible?
- What is the current status?
- What is the priority at feature/backlog level?
- What changed recently?


2. Tenant Direction
-------------------
Current decision: Single tenant.

Meaning:

- All users belong to the same organization.
- There is no project member concept.
- All users can see all projects.
- All projects belong to the same organization.
- Multi-tenancy is not required in the first version.

Future possibility:

- If needed later, add Organization/Tenant table.
- Add TenantId/OrganizationId to users, projects, features, backlog items, tasks,
  and related tables.

Checklist:

[ ] App works as a single-tenant organization app.
[ ] There is no ProjectMember requirement.
[ ] All users can view all projects.
[ ] Admin can manage all projects.


3. User Roles
-------------
Initial roles:

1. Admin
2. User

Admin role:

- Can create projects.
- Can view all projects.
- Can update all projects.
- Can delete/archive all projects.
- Can create, update, and delete all features.
- Can create, update, and delete all backlog items.
- Can create, update, and delete all tasks.
- Can assign features/tasks to users.
- Can manage users if user management exists.
- Can see organization-level reports/dashboard.

User role:

- Can view all projects.
- Cannot create/update/delete projects.
- Can create features under any project.
- Can view all features.
- Can update features.
- Can delete only features created by them.
- Can create backlog items.
- Can view all backlog items.
- Can update backlog items.
- Can delete only backlog items created by them.
- Can create tasks.
- Can view all tasks.
- Can update tasks.
- Can delete only tasks created by them.

Important ownership rule:

- "Own item" means CreatedByUserId equals the current logged-in user id.
- AssignedToUserId does not mean ownership.
- A user may be assigned to an item they did not create.
- A user can update assigned work, but can delete only items they created.

Checklist:

[ ] Admin role exists.
[ ] User role exists.
[ ] Admin can perform all CRUD actions.
[ ] User can only view projects.
[ ] User can create/update features.
[ ] User can delete only own features.
[ ] User can create/update backlog items.
[ ] User can delete only own backlog items.
[ ] User can create/update tasks.
[ ] User can delete only own tasks.
[ ] Delete permission checks CreatedByUserId, not AssignedToUserId.


4. Main Work Hierarchy
----------------------
The app should follow this structure:

Project
  -> Feature
      -> Backlog Item
          -> Task

Notes:

- Project is the top-level container.
- Feature belongs to a project.
- Backlog item belongs to a feature and project.
- Task belongs to a project.
- Task should usually belong to a feature or backlog item, depending on the workflow.

Checklist:

[ ] Project can contain many features.
[ ] Feature belongs to one project.
[ ] Feature can contain many backlog items.
[ ] Backlog item belongs to one feature.
[ ] Backlog item can contain many tasks.
[ ] Task can be connected to project/feature/backlog as required.

A project is a large initiative or work area controlled by admin.

Examples:

- CRM System

Project rules:

- Projects are created by Admin only.
- Projects are updated by Admin only.
- Projects are deleted/archived by Admin only.
- All users can view all projects.
- Project does not have assigned members.

- Completed
- Archived

9. Delete and Archive Rules
---------------------------
Recommended approach: soft delete.

Do not permanently remove rows from the database during normal delete.
Instead, mark the item deleted.

Suggested soft delete fields:

- IsDeleted
- DeletedByUserId
- DeletedAt

Delete rules:

- Admin can delete/archive any project, feature, backlog item, or task.
- User cannot delete projects.
- User can delete only features created by them.
- User can delete only backlog items created by them.
- User can delete only tasks created by them.
- Delete should check CreatedByUserId.
- Delete should not check AssignedToUserId.

Checklist:

[ ] Soft delete is used.
[ ] Deleted items are hidden from normal list pages.
[ ] Admin delete works for all supported items.
[ ] User delete works only for own items.
[ ] User cannot delete project.
[ ] Delete stores DeletedByUserId.
[ ] Delete stores DeletedAt.

-------------------------
Recommended implementation order:

1. Confirm user roles and authentication.
2. Implement project permissions.
3. Add/update project fields and project status.
4. Implement feature entity and feature CRUD.
5. Add feature assignment to user.

7. Implement backlog item entity and backlog CRUD.
8. Add backlog type, priority, and status.
9. Implement task entity and task CRUD.
10. Remove task priority if it exists.
11. Add CreatedByUserId-based delete rules.
12. Add soft delete fields and filtering.
13. Add dashboard counts.
14. Add status history/comments later if needed.

15. Next Features That Can Be Done
----------------------------------
Recommended next feature:

1. My Work page

Purpose:

- Give each user one focused page showing what is assigned to them.
- Turn assignment, status, and priority into a daily work queue.

Suggested behavior:

- Add route: /my-work.
- Show assigned features, backlog items, and tasks for the logged-in user.
- Group work by status.
- Sort feature and backlog work by priority: P1, then P2, then P3.
- Highlight blocked and high-priority items.
- Let users update task status directly from the page.
- Link each row/card back to project, feature, backlog, or task detail.

Why this should be next:

- The app already stores AssignedToUserId, Status, and Priority.
- It adds immediate day-to-day value for every logged-in user.
- It does not require a major database redesign.
- It helps answer: "What should I work on first?"

Suggested implementation checklist:

[ ] Add backend endpoints or query support for current user's assigned features.
[ ] Add backend endpoints or query support for current user's assigned backlog items.
[ ] Add backend endpoints or query support for current user's assigned tasks.
[ ] Add frontend composable for my assigned work.
[ ] Add My Work route.
[ ] Add My Work navigation item in sidebar.
[ ] Build My Work page with sections for Features, Backlog Items, and Tasks.
[ ] Add priority sorting for feature/backlog sections.
[ ] Add quick task status update.
[ ] Add empty states for users with no assigned work.

Good follow-up features after My Work:
